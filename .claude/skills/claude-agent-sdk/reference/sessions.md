# Sessions

Anthropic doc: https://docs.claude.com/en/api/agent-sdk/sessions

## Session id lifecycle

A "session" in the SDK = a Claude conversation. The session id is a UUID generated by the SDK on first turn and persisted in a JSONL file.

- **Created on first turn**: emitted in `system.init.session_id` ([SDKSystemMessage at sdk.d.ts:3282](../../../../node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts)) and again in `result.session_id`.
- **Stored at**: `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`. The JSONL is the SDK's source of truth — every assistant message, user message, tool call, hook event lands there.
- **Resumed via**: `Options.resume: <session-id>`. Loads the JSONL, reconstructs context, continues the conversation.

MultiTable persists the SDK session id on the `AgentSession` row (`s.claudeSessionId`) and reads it on every subsequent `sendTurn`. We capture it from `system.init` ([`agent/sdkAdapter.ts:sdkSystemInit`](../../../../packages/daemon/src/agent/sdkAdapter.ts)).

## `resume` vs `continue` vs `forkSession`

| Option | Meaning |
|---|---|
| `resume: '<id>'` | Resume that exact session. Subsequent assistant messages append to its JSONL. |
| `continue: true` | Resume the most recent session in `cwd` (the SDK figures it out). Useful for one-shot scripts. |
| `resume: '<id>' + forkSession: true` | Branch: copy history up to the resume point, generate a **new** session id, append from there. Original session unchanged. |

MultiTable only uses `resume`. We don't use `continue` (we always know the id) and we don't use `forkSession` (no UI for branching yet — would map to a "duplicate session from this point" feature).

## Helper functions

The SDK exports several session-management helpers (used by the public Claude Code CLI; we don't use them all):

```ts
listSessions(options?: { dir?: string; limit?: number }): Promise<SessionSummary[]>
getSessionMessages(sessionId, options?: { limit?: number }): Promise<SessionMessage[]>
getSessionInfo(sessionId, options?): Promise<SDKSessionInfo | undefined>
renameSession(sessionId, title, options?): Promise<void>
tagSession(sessionId, tags, options?): Promise<void>
deleteSession(sessionId, options?): Promise<void>
forkSession(sessionId, options?): Promise<ForkSessionResult>
importSessionToStore(sessionId, store, options?): Promise<void>
```

We don't currently call these — MultiTable parses the JSONL directly via [`transcripts/parser.ts`](../../../../packages/daemon/src/transcripts/parser.ts) for our transcript browser, cost panel, and labeler. If you ever need session-list functionality and don't want to parse JSONL ourselves, these are the right helpers.

## When the SDK creates a new session vs resumes

Rule: if `resume` (or `continue`) is set in `Options`, the SDK resumes. Otherwise it generates a new session id. There's no "create empty session" call — the session is born from the first `query()`.

This means a fresh MultiTable `AgentSession` row has `s.claudeSessionId = null` until the first turn completes. We omit `resume` on the initial call ([`agent/manager.ts:281`](../../../../packages/daemon/src/agent/manager.ts) does `...(s.claudeSessionId ? { resume: s.claudeSessionId } : {})`).

## `/clear` and the reset endpoint

`POST /api/sessions/:id/reset` ([`api/sessions.ts:326-338`](../../../../packages/daemon/src/api/sessions.ts)) wipes:

- In-memory `s.messages`
- `s.claudeSessionId` (set to null)
- Cost / token / state stats

Next `sendTurn` then creates a new session id from scratch — the JSONL on disk for the old id is left intact (the user can still browse it in the transcript history).

This implements `/clear` semantics in the composer: clear the chat, start fresh, but don't lose history.

## Multi-machine sessions

The SDK supports custom `SessionStore` adapters for storing JSONL outside `~/.claude/projects`. We don't use this. If we ever sync sessions cross-machine, the migration plan in [`docs/SDK_MIGRATION_PLAN.md`](../../../../docs/SDK_MIGRATION_PLAN.md) flags it as future work.

## Common mistakes

- **Treating `s.claudeSessionId` as truth before the first turn.** It's `null` until `system.init` fires. Don't query the JSONL based on it during session creation; wait until the first turn returns.
- **Forking by deleting and recreating.** That loses history. Use `forkSession: true` to keep the prior context.
- **Hand-editing the JSONL.** The SDK appends; if your edit breaks JSON parsing, the session is corrupt and `resume` will fail. Use `deleteSession` or move/archive the file instead.
